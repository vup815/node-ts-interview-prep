Q1. Event Loop 怎麼運作？

要點：libuv 實作 · 六個 phases · microtask 每個 phase 之間完整清空

完整回答：

"Event loop 是由 libuv 實作的。它讓單執行緒的 JavaScript 能處理非阻塞的 I/O 並行。

它循環六個 phases：timers（setTimeout/setInterval）、pending callbacks、idle/prepare（內部用）、poll（I/O callbacks）、check（setImmediate）、close callbacks。

關鍵是 microtask queue（nextTick 優先，Promise 次之）會在每個 phase 之間被完整清空。所以 promise 的 .then 會比 setTimeout(0) 先跑，因為後者是 macrotask，要等 timers phase。

實務影響：如果某個 CPU 密集工作佔住主執行緒，event loop 就無法處理任何 I/O — 整個 server 會凍結。"

Q2. setTimeout(0) vs process.nextTick

要點：nextTick 一定先執行 · recursive nextTick 會餓死 event loop

完整回答：

"setTimeout(cb, 0) 是 macrotask — 在 timers phase 執行。process.nextTick(cb) 是 microtask — 在每個 phase 之間、macrotask 之前被清空。所以 nextTick 一定先執行，這是 Node 的保證。

但 nextTick 有個陷阱：如果你在 nextTick callback 裡又遞迴呼叫 nextTick，nextTick queue 永遠清不空，event loop 走不到 poll phase，所有 I/O 都會被餓死。

現代寫法我會用 queueMicrotask() 取代 nextTick，需要延後到 I/O 之後的工作用 setImmediate()。"

Q3. Partial / Pick / Omit

要點：Partial=全部 optional（PATCH）· Pick=選子集（查詢回應）· Omit=去掉欄位（藏機密）· 組合：Partial<Omit<User,'id'>>
Utility做什麼情境
Partial<T>全部欄位變 optionalPATCH request body
Pick<T, K>只保留 K 欄位查詢 API 只回傳特定欄位
Omit<T, K>移除 K 欄位不回傳機密/敏感欄位
陷阱（面試追問）：Partial 是淺層的 — 只影響最外層欄位，巢狀物件不會。面試官等你講出這個。

"我組合使用：Partial<Omit<User, 'id'>> = id 不能改，其他欄位可選改 — 這是 PATCH 的完整答案。保留的欄位少用 Pick，移除的欄位少用 Omit。"

Q4. Interface vs Type

要點：唯一真正的差別是 declaration merging（interface 可以，type 不行）· 預設用 type，擴充第三方型別才用 interface

"Interface 和 type 在物件 shape 上幾乎等價，真正的差別是 interface 可以 declaration merging — 重複宣告會合併，type 重複宣告會報錯。

Type 比較靈活，可以表達 union、tuple、primitive alias、utility/mapped types — interface 做不到。

我的原則是：預設用 type 定義所有資料形狀。唯一用 interface 的時機是擴充第三方型別 — 比如往 Express 的 Request 加 user 屬性，那必須用 interface 才能 merge。"

Q5. 型別化 API 回應

要點：discriminated union · 共同 literal 欄位（status）當 discriminant · default: never exhaustiveness check
type ApiResult<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }

"好處是無效狀態在型別層面就不存在 — 不可能同時有 data 和 error。使用端用 switch 收窄，每個 case 自動知道有哪些欄位。

我還會加 default: never 做 exhaustiveness check — 以後加新狀態，編譯器會強迫我處理它。"

Q6. Streams

要點：chunk 流式處理 · 4 種型別 · backpressure · 2GB 檔案只佔 ~64KB

"Streams 是處理資料的抽象介面，以 chunk 為單位流式處理，而不是一次載入全部。

四種型別：Readable（讀取來源）、Writable（寫入目標）、Duplex（可讀可寫，如 TCP socket）、Transform（讀取→轉換→寫出，如 gzip）。

好處是記憶體效率：2GB 檔案用 readFile 佔 2GB RAM，用 stream 一次只處理 ~64KB。

Streams 用 .pipe() 串接，它會自動處理 backpressure — 寫入端跟不上時暫停讀取端，避免記憶體爆掉。"

Q7. 單執行緒怎麼並行？（最大迷思！）

要矯正的迷思：Node 並行靠的是「單執行緒 + 非阻塞 I/O + event loop」，不是 thread pool。HTTP/TCP 不走 thread pool，是作業系統層面的非同步。

"Node 是單執行緒，但能處理大量請求，靠的是非阻塞 I/O + event loop。HTTP/TCP 這類網路 I/O 由作業系統層面非同步處理，完成後透過 event loop 通知主執行緒。

但 fs、crypto、DNS 這類 blocking 系統呼叫，會交給 libuv thread pool（預設 4 個執行緒）。

CPU 密集工作是 Node 的弱點 — 直接跑在主執行緒，佔住 event loop，所有請求凍結。解法：worker_threads、cluster、或改用內建 thread pool 函式。"

操作誰處理
HTTP / TCP 網路作業系統（非同步）
檔案讀寫 fsthread pool
crypto (pbkdf2)thread pool
DNS lookupthread pool

追問：請求會排隊嗎？

HTTP 請求本身不會排隊 — OS 層並行處理。但如果 handler 內做了 fs/crypto，那些操作會排 thread pool（4 個執行緒，第 5 個開始排隊）。

深入討論 1：OS 怎麼通知 event loop？

要點：epoll/kqueue · poll phase 就是 block 在 epoll_wait() 上 · callback 排進 poll phase

底層機制：作業系統提供「等 I/O 事件」的系統呼叫 — Linux 是 epoll，macOS 是 kqueue。libuv 把 socket 註冊進去，poll phase 就 block 在 epoll_wait() 上。資料到了 OS 喚醒它，libuv 把對應 callback 排進 poll phase。

什麼完成callback 進哪個 phase
檔案讀取、網路請求、socketpoll
setTimeout / setIntervaltimers
setImmediatecheck

等資料的是 OS 核心，不是 JS 執行緒。執行緒只是 block 在 epoll_wait() 等 OS 叫醒，不佔 CPU。

深入討論 2：microtask 細節

要點：每個 phase 後完整清空 · nextTick 先、Promise 次之 · 清空中產生的新 microtask 會繼續清
setTimeout(() => console.log('A'), 0);
Promise.resolve().then(() => {
  console.log('B');
  setTimeout(() => console.log('C'), 0);
});
process.nextTick(() => console.log('D'));

// 輸出：D, B, A, C
// nextTick 優先 → Promise → 第一個 timer → 第二個 timer（同 phase 內）

深入討論 3：async/await yield（最經典陷阱）

核心規則：await 永遠把控制權交還給呼叫者，就算 Promise 已 resolved。
async function foo() {
  console.log('1');
  await bar();      // 暫停 foo 自己
  console.log('3'); // 續段被排成 microtask
}
async function bar() { console.log('2'); }
foo();
console.log('4');

// 輸出：1, 2, 4, 3  （不是 1, 2, 3, 4！）

// 如果 bar() 沒有 await：
// 輸出：1, 2, 3, 4  （bar 同步執行，foo 接著跑）

await 暫停的是「包含 await 的函式」（foo），控制權回到呼叫 foo 的地方（全域）。

深入討論 4：setImmediate 的應用

  • 排在目前 I/O 之後：在 poll phase 的 callback 裡，setImmediate 保證在下一輪 timers 前執行，不會延遲其他 I/O
  • 避免 blocking / yield：長遞迴任務用 setImmediate 每輪 yield 給 event loop，比 nextTick 安全（nextTick 會餓死 I/O）

"setImmediate = 我接下來馬上要做的，但先讓 I/O 呼吸。process.nextTick = 我插隊，誰都別攔我。"
