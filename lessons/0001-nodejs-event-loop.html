Node.js Interview

Lesson 1: The Event Loop

The single highest-signal topic in Node.js interviews. If you control the event-loop conversation, you control the round.

Mission: Backend engineer interview prep

Why This Matters

Every Node.js interview includes at least one output-order puzzle or "explain how async works" question. Interviewers report that the event loop is the #1 separator between surface-level and deep understanding. This lesson gives you both the mental model and the verbal script.

1. The Mental Model

Single thread + libuv

JavaScript runs on one thread. It cannot do two things at once. When you call fs.readFile or setTimeout, Node hands the work to libuv — a C library that manages I/O, timers, and a thread pool. When the work finishes, libuv queues a callback and the event loop picks it up when the JS call stack is empty.

Key insight: "Single-threaded" means your JavaScript runs on one thread. libuv's thread pool (default: 4 threads) handles blocking operations. The event loop is the bridge between them.

The Six Phases

The event loop cycles through six phases. The three you'll be asked about in interviews:

PhaseWhat runsKey API
timersCallbacks from expired setTimeout / setIntervalsetTimeout(fn, 0)
pending callbacksDeferred system callbacks (e.g., TCP errors)internal
idle / prepareInternal libuv bookkeepinginternal
pollI/O callbacks (file reads, network, etc.)fs.readFile, http
checksetImmediate callbackssetImmediate(fn)
close callbacksCleanup events (e.g., socket.on('close'))internal

Microtasks — The Trap Door

Between every phase, the event loop checks the microtask queues. They have higher priority than any macrotask.

QueuePriorityAPI
nextTick queueHighestprocess.nextTick(fn)
Promise microtask queueSecondPromise.resolve().then(fn), queueMicrotask(fn), await

Full Execution Order

1. Run current synchronous code (call stack)
2. Drain entire nextTick queue
3. Drain entire promise microtask queue
4. Run one macrotask from current phase (e.g., one timer callback)
5. Drain entire nextTick queue again
6. Drain entire promise microtask queue again
7. Move to next phase, repeat from step 4
Starving the loop: Recursive process.nextTick before the event loop advances prevents the poll phase from running. This is why Node warns about it. Use setImmediate instead to yield to I/O.

3. Output-Order Puzzles

Try each puzzle. Predict the output out loud before clicking to reveal.

Puzzle 1: Basic ordering

console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

console.log('4');

Output: 1, 4, 3, 2

Why: 1 and 4 run synchronously first. Promise .then is a microtask — runs after the call stack is empty, before the next macrotask. setTimeout(0) is a macrotask — it runs in the next timers phase.

Puzzle 2: nextTick vs Promise

Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');

Output: sync, nextTick, promise

Why: sync runs first. The nextTick queue drains before the promise queue — nextTick has higher priority among microtasks.

Puzzle 3: Inside an I/O callback — setImmediate vs setTimeout

const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});

Output: immediate, timeout

Why: Inside an I/O callback, the event loop is in the poll phase. After poll, it moves to check (setImmediate), then close callbacks, then back to timers (setTimeout). So setImmediate always wins inside I/O.

Outside I/O, the order of setTimeout vs setImmediate is non-deterministic — it depends on how long the timer takes to enter the timers phase.

Puzzle 4: Nested microtasks

process.nextTick(() => {
  console.log('nextTick 1');
  process.nextTick(() => console.log('nextTick 2'));
});

Promise.resolve().then(() => {
  console.log('promise 1');
  process.nextTick(() => console.log('nextTick 3'));
});

console.log('sync');

Output: sync, nextTick 1, nextTick 2, promise 1, nextTick 3

Why: The entire nextTick queue drains before the promise queue starts. Even though nextTick 2 is enqueued inside a nextTick callback, it drains in the same microtask drain. After the nextTick queue is empty, the promise queue starts. But nextTick 3 is enqueued inside a promise callback — it runs in the next microtask drain (after the promise queue empties, before the next phase).

Puzzle 5: Async/await — the trap

async function foo() {
  console.log('a');
  await bar();
  console.log('c');
}

async function bar() {
  console.log('b');
}

foo();
console.log('d');

Output: a, b, d, c

Why: foo() runs synchronously until it hits await. console.log('a') runs, then bar() is called. bar() runs synchronously (console.log('b')) and returns a resolved promise. The await suspends foo and returns execution to the caller. console.log('d') runs. The continuation of foo (the part after await) is queued as a microtask. It runs after the call stack empties.

Interview trap: Many candidates think c runs before d. They miss that await yields to the caller.

4. Interview Answer Script

When the interviewer asks "Explain the event loop," here's your script:

"The event loop is what lets Node.js handle thousands of concurrent connections on a single thread. libuv — the C library underneath — actually runs the loop, cycling through phases: timers, pending callbacks, poll, check, and close. Each phase has a FIFO queue of callbacks.

"Between each phase, Node drains two microtask queues: first process.nextTick, then promise microtasks. This is why nextTick runs before .then callbacks, and why a deeply recursive nextTick can starve I/O.

"The key mental model: synchronously queued microtasks run before any macrotask. So Promise.resolve().then(...) runs before setTimeout(...), even with a zero delay. And inside an I/O callback, setImmediate fires before the next setTimeout because check phase comes before the next timers phase."

Why this script works: It mentions libuv (shows depth), names the phases (shows structure), explains microtask vs macrotask (shows precision), and gives an example (shows practical understanding). This is the arc of a strong answer.

5. Common Follow-Up Questions

Q: "What runs on the libuv thread pool?"

A: File system operations (fs), DNS (dns.lookup), and some crypto (crypto.pbkdf2, crypto.randomBytes). Network I/O (HTTP, TCP) uses the OS kernel — no thread pool.

Q: "What happens when the poll phase has no timers and no I/O?"

A: The poll phase checks for setImmediate callbacks. If any exist, it immediately moves to the check phase. If none, it blocks waiting for I/O events. If a timer is expiring soon, it skips the wait and moves to the timers phase.

Q: "Does the event loop run forever?"

A: No. The event loop stops when there are no more handles (timers, I/O sockets) or requests to process. The loop calls uv_run — when libuv returns, Node exits.
