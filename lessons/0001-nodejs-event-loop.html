Node.js 面試

Lesson 1: Event Loop

Node.js 面試中最重要的題目。能講清楚 event loop，就能掌握整個面試的節奏。

為什麼這題重要

每場 Node.js 面試至少會有一題 event loop。面試官回報，event loop 是區分表面理解和深層理解的第一道關卡。這堂課給你完整的心理模型和口頭回答腳本。

1. 心理模型

單執行緒 + libuv

JavaScript 跑在一個執行緒上。它無法同時做兩件事。當你呼叫 fs.readFile 或 setTimeout，Node 把工作交給 libuv — 一個 C 語言寫的函式庫，負責管理 I/O、計時器和一個執行緒池。工作完成後，libuv 把 callback 排入佇列，等 JS 呼叫栈空了之後，event loop 再來處理。

關鍵觀念：「單執行緒」指的是你的 JavaScript 程式碼跑在一個執行緒上。libuv 的執行緒池（預設 4 個執行緒）負責處理阻塞操作（檔案讀寫、加密）。Event loop 是連接兩者的橋樑。

六個 Phases

Phase執行的東西相關 API
timers到期的 setTimeout / setInterval callbacksetTimeout(fn, 0)
pending callbacks延遲的系統 callback（如 TCP 錯誤）內部使用
idle / preparelibuv 內部記帳內部使用
pollI/O callback（檔案讀取、網路）fs.readFile、http
checksetImmediate callbacksetImmediate(fn)
close callbacks清理事件（如 socket.on('close')）內部使用

Microtask — 陷阱所在

Node 11+：在每個 macrotask callback 執行完之後，event loop 都會清空 microtask 佇列，然後才處理同一個 phase 的下一個 callback。這是為了與瀏覽器行為一致（HTML5 規範）。

Node 10 及之前的行為則是在整個 phase 的所有 callback 都執行完後才清空 microtask。這是面試中可能會問的歷史差異。

Microtask 的優先級高於任何 macrotask。

佇列優先級API
nextTick 佇列最高process.nextTick(fn)
Promise microtask 佇列第二Promise.resolve().then(fn)、queueMicrotask(fn)、await

完整執行順序（Node 11+）

1. 執行當前的同步程式碼（call stack）
2. 清空整個 nextTick 佇列
3. 清空整個 Promise microtask 佇列
4. 執行一個目前 phase 的 macrotask（例如一個 timer callback）
5. 再次清空整個 nextTick 佇列
6. 再次清空整個 Promise microtask 佇列
7. 執行同一個 phase 的下一個 macrotask，重複步驟 5-6
   直到目前 phase 的佇列清空
8. 移到下一個 phase，重複步驟 4-7
餓死 Event Loop：遞迴呼叫 process.nextTick 會讓 nextTick 佇列永遠清不空，event loop 永遠走不到 poll phase，所有 I/O 都無法處理。遞迴 Promise.resolve().then() 也會有一樣的效果。

3. 輸出順序題

先預測輸出結果，再點開看答案。

題目 1：基本順序

console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');

輸出：1, 4, 3, 2

1 和 4 先同步執行。Promise 的 .then 是 microtask — 在 call stack 清空後、下一個 macrotask 之前執行。setTimeout(0) 是 macrotask — 在下一個 timers phase 執行。

題目 2：nextTick vs Promise

Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');

輸出：sync, nextTick, promise

nextTick 佇列在 Promise 佇列之前清空 — nextTick 在 microtask 中有最高優先級。

題目 3：在 I/O callback 裡 — setImmediate vs setTimeout

const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});

輸出：immediate, timeout

在 I/O callback 裡面時，event loop 正在 poll phase。poll 之後會到 check（setImmediate），然後 close callbacks，最後才回到 timers（setTimeout）。所以在 I/O 內部，setImmediate 永遠比 setTimeout 先跑。

在 I/O 外部，setTimeout 和 setImmediate 的順序是不確定的 — 取決於計時器何時到期。

題目 4：巢狀 Microtask

process.nextTick(() => {
  console.log('nextTick 1');
  process.nextTick(() => console.log('nextTick 2'));
});
Promise.resolve().then(() => {
  console.log('promise 1');
  process.nextTick(() => console.log('nextTick 3'));
});
console.log('sync');

輸出：sync, nextTick 1, nextTick 2, promise 1, nextTick 3

整個 nextTick 佇列在 Promise 佇列之前清空。即使 nextTick 2 是在 nextTick callback 裡面被加入的，它仍然在同一次清空中執行。nextTick 佇列清空後，Promise 佇列才開始。nextTick 3 是在 Promise callback 裡加入的，它會在下一次 microtask 清空時執行。

題目 5：Async/await — 經典陷阱

async function foo() {
  console.log('a');
  await bar();
  console.log('c');
}
async function bar() { console.log('b'); }
foo();
console.log('d');

輸出：a, b, d, c

await 暫停 foo，把控制權交還給呼叫者（全域範圍）。foo 的續段（await 之後的部分）被排成 microtask，在 call stack 清空後執行。很多人以為 c 在 d 之前，但 await 永遠把控制權交還給呼叫者。

4. 面試完整回答

當面試官問「解釋 event loop」，用這份腳本：

"Event Loop 是 Node.js 底層由 libuv 實作的核心機制。它讓 Node.js 能夠在單一執行緒上，高效處理大量並行的 I/O 與非同步操作 — 非同步 I/O 不會被卡住，但 CPU 密集任務仍然會阻塞主執行緒。

整個 Event Loop 會不斷地循環經過六個 phase，每個 phase 都有自己的 callback 佇列。第一個是 timers，負責執行已經到期的 setTimeout 和 setInterval。接下來是 pending callbacks，處理一些系統層級的延遲 I/O callback。然後是 idle 和 prepare，這兩個主要是 libuv 內部使用。

再來就是最核心的 poll phase，它做兩件事：抓取新的 I/O 事件並執行對應 callback，以及在必要時決定要不要阻塞等待。接著進入 check phase，專門執行 setImmediate 的 callback。最後是 close callbacks，處理像 socket 關閉這類 close 事件。

每執行完一個 callback，Node 就會立刻清空一次 microtask 佇列。順序上，process.nextTick 佇列優先於 Promise 的 microtask 佇列，而且會反覆清空，直到兩個佇列都空了，才會繼續往下一個 callback 或下一個 phase 前進。

正因為這個機制，Promise.then 一定會比 setTimeout(fn, 0) 更早執行。因為前者屬於 microtask，會在當前 callback 結束後立刻處理；後者必須等到下一輪的 timers phase 才有機會被執行。

一般情況下，setTimeout(0) 和 setImmediate 誰先跑是不確定的，取決於當下 Event Loop 的狀態與系統負載。但如果你是在一個 I/O callback 裡面比較這兩者，結果就固定了。因為當下已經在 poll phase，下一個 phase 就是 check，所以 setImmediate 永遠會先於 setTimeout(0) 執行。

process.nextTick 的優先級非常高。如果你在 callback 裡不斷遞迴呼叫 process.nextTick，microtask 佇列就永遠清不完，Event Loop 永遠走不到下一個 phase，結果就是所有的 I/O、timer、setImmediate 全部被餓死。"

為什麼這段話有效：提到 libuv（展現深度）、完整說出六個 phase 名稱與用途（展現結構）、解釋 microtask 在每個 callback 後的清空機制（展現精確度）、區分「不確定」與「確定」的 setImmediate 順序（展現經驗）、說明 nextTick 遞迴的餓死風險（展現實戰理解）。

5. 常見追問題

追問：「什麼東西跑在 libuv 的執行緒池上？」

檔案系統操作（fs）、DNS（dns.lookup）、部分加密操作（crypto.pbkdf2、crypto.randomBytes）。網路 I/O（HTTP、TCP）使用作業系統核心 — 不經過執行緒池。

追問：「poll phase 如果沒有 timer 也沒有 I/O 會發生什麼事？」

Poll phase 會檢查是否有 setImmediate callback。如果有，立刻移到 check phase。如果沒有，它會 blocking 等待 I/O 事件。如果有一個 timer 即將到期，它會跳過等待直接移到 timers phase。

追問：「Event loop 會永遠跑下去嗎？」

不會。當沒有 handle（timer、I/O socket）或 request 需要處理時，event loop 就會停止。Loop 在 libuv 裡是透過 uv_run 執行的 — 當 libuv 回傳時，Node 就結束了。
