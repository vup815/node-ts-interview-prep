TypeScript Interview

Lesson 6: Discriminated Unions

Backend 工程師最常用的型別模式 — 用一個欄位區分型別的「狀態」。

Prerequisite: Lesson 4 (narrowing)

為什麼要學這個

面試中很常被問：「怎麼型別化一個 API 回應？」或「怎麼處理多種可能的狀態？」Discriminated unions 是標準答案。它是「type-safe 的 enum + switch」。

1. 問題：不用 discriminated union 會怎樣

// ❌ 壞習慣：把所有欄位塞進一個型別，用 null 表示「沒有」
interface ApiResult<T> {
  ok: boolean
  data: T | null
  error: string | null
  loading: boolean
}

// 問題 1：無效狀態可以被建出來
const bad: ApiResult<User> = {
  ok: true,
  data: null,      // ok=true 但 data 是 null？
  error: 'error',  // 同時有 data 和 error？
  loading: true,   // 又 loading 又 ok？
}
// ❌ 編譯器沒有抓錯 — 狀態互相矛盾

// 問題 2：使用端要一直檢查
if (res.ok) {
  res.data // 可能是 null，要再 null check
} else {
  res.error // 可能是 null，要再 null check
}
重點：這種寫法讓「矛盾的狀態」在型別層面合法。資料只有兩種合理狀態，但你允許了 2^4 = 16 種組合。

2. Discriminated Union：正確做法

核心概念：每個狀態一個物件，用一個共同的 literal 欄位（discriminant）來區分。

type ApiResult<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }

// 現在無效狀態不可能存在
const bad = { status: 'success', message: 'oops' }
// ❌ Error: 'message' does not exist in type { status: 'success'; data: T }

const good = { status: 'success', data: { id: 1, name: 'Ada' } }
// ✅ 合法 — success 必須有 data

status 就是 discriminant — 它是一個 literal type（'loading' | 'success' | 'error'），不是 string。TypeScript 用它來判斷是哪一個 variant。

3. 使用：switch + narrowing

function render(result: ApiResult<User>): string {
  switch (result.status) {
    case 'loading':
      return '載入中...'          // result 收窄成 loading variant
    case 'success':
      return `Hello ${result.data.name}`  // ✅ 有 data
    case 'error':
      return `錯誤：${result.message}`     // ✅ 有 message
    default:
      const _exhaustive: never = result   // 防漏 case
      return _exhaustive
  }
}

每個 case 裡，TypeScript 自動知道有哪些欄位可用 — 不用 null check。

4. 真實世界的例子

範例 A：Fetch 回應

type FetchState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }

// 你永遠不會誤用 idle 狀態的 data — 型別不允許

範例 B：WebSocket 訊息

type ServerMessage =
  | { type: 'chat'; sender: string; text: string }
  | { type: 'join'; username: string }
  | { type: 'leave'; username: string }
  | { type: 'system'; code: number }

function handleMessage(msg: ServerMessage) {
  switch (msg.type) {
    case 'chat':
      console.log(`${msg.sender}: ${msg.text}`)
      break
    case 'join':
      console.log(`${msg.username} 加入了`)
      break
    // system 和 leave 沒處理 — TypeScript 不會警告（除非有 never check）
  }
}

範例 C：驗證結果（面試常問）

type ValidationResult =
  | { ok: true; value: number }
  | { ok: false; errors: string[] }

function parsePositiveInt(input: string): ValidationResult {
  const n = Number(input)
  if (!Number.isInteger(n) || n <= 0) {
    return { ok: false, errors: ['必須是正整數'] }
  }
  return { ok: true, value: n }
}

const result = parsePositiveInt('abc')
if (result.ok) {
  result.value // ✅ number
} else {
  result.errors // ✅ string[]
}

5. 搭配 utility types

type ApiResult<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }

// 只取 success 狀態（過濾 union）
type Success<T> = Extract<ApiResult<T>, { status: 'success' }>
// Result: { status: 'success'; data: T }

// 把 data 變可選（像是 Partial 但只作用於某欄位）
type MaybeData<T> = {
  [K in keyof ApiResult<T>]: K extends 'data' ? T | null : ApiResult<T>[K]
}

6. 面試 script

當面試官問「怎麼型別化 API 回應」：

"我用 discriminated union。每個狀態一個 object，用一個共同欄位（像是 status）當 discriminant。

"這樣做有三個好處：第一，無效狀態在型別層面就不存在 — 不可能同時有 data 和 error。第二，使用端用 switch 收窄後，每個 case 都明確知道自己有哪些欄位，不用 null check。第三，加上 never exhaustiveness check 後，如果以後加新狀態，編譯器會強迫我處理它。

"這是我在後端最常用的型別模式 — API 回應、WebSocket 訊息、驗證結果都用它。"

7. 練習題

Puzzle 1: 把這個壞型別改寫成 discriminated union：

interface PaymentResult {
  success: boolean
  transactionId?: string
  errorMessage?: string
}
type PaymentResult =
  | { success: true; transactionId: string }
  | { success: false; errorMessage: string }

Puzzle 2: 這個 switch 少了哪個 case 的處理？

type Event =
  | { kind: 'created'; id: number }
  | { kind: 'updated'; id: number; changes: string[] }
  | { kind: 'deleted'; id: number }

function handle(e: Event) {
  switch (e.kind) {
    case 'created': console.log('create', e.id)
    case 'updated': console.log('update', e.id, e.changes)
    case 'deleted': console.log('delete', e.id)
  }
}

語法上沒有少，但少了 default: never check。如果未來加一個 { kind: 'archived' }，這個 switch 不會報錯，會靜默漏掉。加上 exhaustiveness check 才是完整的寫法。

Puzzle 3: 寫一個 discriminated union，代表一個檔案上傳的三種狀態：uploading（有 progress 百分比）、success（有 url）、failed（有 reason）。

type UploadState =
  | { status: 'uploading'; progress: number }
  | { status: 'success'; url: string }
  | { status: 'failed'; reason: string }
