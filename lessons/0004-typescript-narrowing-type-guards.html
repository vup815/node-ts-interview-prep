TypeScript Interview

Lesson 4: Narrowing & Type Guards

How to turn a vague type into a precise one — one of the most practical skills in TypeScript interviews.

Prerequisites: Lesson 2b (utility types)

Why This Matters

In real code — and in interviews — you constantly receive data of a broad type and need to work with it safely. Narrowing is how you refine that broad type into something useful. Without it, everything is any or unknown and you lose type safety.

1. What is Narrowing?

Narrowing is TypeScript's process of reducing a union type to a specific member of that union, based on a runtime check.

// Broad type
function process(value: string | number) {
  // Here, `value` is string | number — too vague to do anything useful

  if (typeof value === 'string') {
    // Inside this block, `value` is narrowed to `string`
    console.log(value.toUpperCase());  // ✅ OK
  } else {
    // Inside this block, `value` is narrowed to `number`
    console.log(value.toFixed(2));     // ✅ OK
  }
}

The typeof check acts as a type guard — it tells TypeScript to trust that inside the if block, the type is string.

2. typeof — The Most Common Guard

function format(input: string | number | boolean): string {
  if (typeof input === 'string') {
    return input.toUpperCase();
  }
  if (typeof input === 'number') {
    return input.toFixed(2);
  }
  // At this point, TypeScript knows input is boolean
  return input ? 'yes' : 'no';
}

What typeof can check

  • 'string', 'number', 'boolean', 'symbol', 'bigint', 'undefined', 'object', 'function'
  • ⚠️ typeof null === 'object' — this is a JS bug. Use a separate null check.

3. instanceof — For Classes

class ApiError extends Error {
  constructor(public statusCode: number, message: string) {
    super(message);
  }
}

function handleError(err: Error | string) {
  if (err instanceof ApiError) {
    // narrowed to ApiError — has .statusCode
    console.log(`API ${err.statusCode}: ${err.message}`);
  } else if (err instanceof Error) {
    // narrowed to Error
    console.log(`General error: ${err.message}`);
  } else {
    // narrowed to string
    console.log(`String message: ${err}`);
  }
}

4. The 'in' Operator — Checking Properties

interface Car { wheels: number; drive(): void; }
interface Boat { length: number; sail(): void; }

function operate(vehicle: Car | Boat) {
  if ('drive' in vehicle) {
    // narrowed to Car
    vehicle.drive();
  } else {
    // narrowed to Boat
    vehicle.sail();
  }
}

'property' in obj checks if a property exists at runtime. TypeScript uses this to narrow the type to whichever member has that property.

5. Discriminated Unions — The Cleanest Pattern

Instead of checking which properties exist, check a common literal discriminant property:

type ApiResult<T> =
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }
  | { status: 'loading' };

function handleResult(result: ApiResult<User>) {
  switch (result.status) {
    case 'success':
      // narrowed: result.data is User ✅
      console.log(result.data.name);
      break;
    case 'error':
      // narrowed: result.message is string ✅
      console.error(result.message);
      break;
    case 'loading':
      // narrowed: no data, no message — just loading
      console.log('Loading...');
      break;
  }
}
Interview script: "I use discriminated unions with a common status or kind field. The compiler narrows inside each case, so accessing .data on 'loading' is a compile error."

6. User-Defined Type Guards

Sometimes typeof or instanceof isn't enough. You can write a custom type guard using the value is Type syntax:

interface User { name: string; email: string; }
interface Admin extends User { role: 'admin'; }

function isAdmin(user: User): user is Admin {
  return 'role' in user && user.role === 'admin';
}

function processUser(user: User) {
  if (isAdmin(user)) {
    // narrowed to Admin — has .role
    console.log(`Admin: ${user.name}, role: ${user.role}`);
  } else {
    // narrowed to User (not Admin)
    console.log(`User: ${user.name}`);
  }
}

The return type user is Admin tells TypeScript: "if this function returns true, treat the argument as Admin."

7. Exhaustiveness Check with never

When you add a new variant to a union, you want the compiler to warn you about unhandled cases:

type Shape =
  | { kind: 'circle'; radius: number }
  | { kind: 'square'; side: number }
  | { kind: 'triangle'; base: number; height: number };  // new!

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle':
      return Math.PI * s.radius ** 2;
    case 'square':
      return s.side ** 2;
    default:
      // Error if any case is missing:
      // Type 'triangle' is not assignable to type 'never'
      const _exhaustive: never = s;
      return _exhaustive;
  }
}
Interview trap: Without the never default, adding triangle would compile silently. The function would return undefined at runtime. The never check catches this at compile time.

9. Puzzles

Puzzle 1: What is the narrowed type of x inside each branch?

function test(x: string | number | null) {
  if (typeof x === 'string') { /* ??? */ }
  else if (typeof x === 'number') { /* ??? */ }
  else { /* ??? */ }
}

string, number, null — the else branch gets whatever remains after the guards.

Puzzle 2: What is the problem with this code?

function getLength(x: string | string[]) {
  if (typeof x === 'object') {
    return x.length;
  }
  return x.length;
}

typeof null === 'object' — so if x is somehow null, the first branch would crash. Use Array.isArray(x) instead when checking for arrays.

Puzzle 3: Without adding the never check in the default branch, what would happen if someone adds { kind: 'triangle'; base: number; height: number } to the Shape union?

The function would compile fine, but at runtime area({ kind: 'triangle', base: 3, height: 4 }) would return undefined — no error, no warning. The never check forces you to handle every variant.

10. Interview Answer Script

When the interviewer says "How does TypeScript narrowing work?"

"Narrowing is TypeScript's ability to refine a union type based on runtime checks. The most common guards are typeof for primitives, instanceof for classes, and 'property' in obj for checking property existence.

"For object types with multiple variants, I use discriminated unions — each member has a literal kind or status property, and a switch statement narrows per case. I always add a default: never branch as an exhaustiveness check so the compiler tells me when I've missed a variant.

"For complex logic, I write custom type guards with the value is Type return syntax — they let me encapsulate the runtime check while keeping the narrowed type downstream."
