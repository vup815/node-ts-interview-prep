TypeScript 面試

Lesson 11: satisfies & as const

TypeScript 4.9+ 的現代功能 — 2026 面試已經在問了。考你對型別系統的理解深度。

為什麼這題重要

面試官問 satisfies 和 as const 不是考語法，是考你能不能理解 TypeScript 型別系統中一個根本的 tension：「型別檢查」和「型別拓寬（widening）」之間的衝突。一個型別越安全就越寬（失去精確度），越精確就越難保證安全。這兩個功能就是在解決這個問題。

1. 問題：型別斷言（as）會拓寬

// 你有一個 config object，想確保它符合某個型別
const config = {
  port: 3000,
  debug: true,
} as Record<string, unknown>;

config.port; // 型別：unknown ❌ — 我們失去了 number 型別！
config.debug; // 型別：unknown ❌

用 as（型別斷言）時，你在告訴 TypeScript「相信我，它就是這個型別」。但副作用是 TypeScript 會拓寬它 — 你失去了原本的 literal 型別。

為什麼會這樣？

as Type 的語意是「把這個值當作 Type 看待」— 它會覆蓋 TypeScript 自己推斷的型別。所以 TypeScript 放棄了原本推斷的精確型別，改用你指定的寬型別。

2. satisfies：型別檢查但不拓寬

const config = {
  port: 3000,
  debug: true,
} satisfies Record<string, unknown>;

config.port;  // 型別：number ✅ — 保留了！
config.debug; // 型別：boolean ✅

satisfies 做的事：檢查值是否符合型別，但不改變 TypeScript 推斷的型別。你同時得到安全驗證 + 精確型別。

3. 實際面試範例

type Color = 'red' | 'green' | 'blue';
type Config = Record<string, unknown>;

// ❌ 用 as — 失去 union 型別
const palette1 = {
  primary: 'blue',
  secondary: 'green',
} as Config;
// palette1.primary 是 unknown — 無法當 Color 使用

// ✅ 用 satisfies — 保留 literal 型別
const palette2 = {
  primary: 'blue',
  secondary: 'green',
} satisfies Config;
// palette2.primary 是 'blue'（literal）— 可以當 Color 使用

function setColor(c: Color) { /* ... */ }
setColor(palette2.primary); // ✅ OK — 'blue' 是 Color 的一種
setColor(palette1.primary); // ❌ Error — 'unknown' 不是 Color

4. 另一個常見場景：物件 key 的驗證

// 你想要一個物件，key 只能是特定字串，但 value 可以是不同型別
type RouteMap = Record<string, { path: string; component: string }>;

const routes = {
  home: { path: '/', component: 'HomePage' },
  about: { path: '/about', component: 'AboutPage' },
  // 不小心打錯字：
  // contatc: { path: '/contact', component: 'ContactPage' },
} satisfies RouteMap;
// ❌ Error: 'contatc' 拼錯了 — satisfies 會幫你抓到！

5. as const — Literal 型別

as const 讓整個值變成深度 readonly，並把所有型別收窄到 literal，而不是拓寬後的型別。

// 沒用 as const — 被拓寬
const roles = ['admin', 'user', 'guest'];
// 型別：string[] ❌ — 失去了具體的字串

// 用 as const — 保留 literal
const roles = ['admin', 'user', 'guest'] as const;
// 型別：readonly ['admin', 'user', 'guest'] ✅

// 實戰用法：從陣列取出 union 型別
type Role = typeof roles[number]; // 'admin' | 'user' | 'guest'

// 配合 exhaustive switch
function handleRole(role: Role) {
  switch (role) {
    case 'admin': /* ... */ break;
    case 'user':  /* ... */ break;
    case 'guest': /* ... */ break;
    default:
      const _exhaustive: never = role; // 如果以後加新角色，編譯器會報錯
      break;
  }
}

6. 組合使用：最強模式

const config = {
  apiUrl: 'https://api.example.com',
  port: 3000,
  roles: ['admin', 'user'] as const,
  features: {
    darkMode: true,
    beta: false,
  },
} satisfies Record<string, unknown>;

// 全部保留了精確型別：
// config.apiUrl — literal 'https://api.example.com'
// config.port — number
// config.roles — readonly ['admin', 'user']
// config.features.darkMode — boolean
// 但同時都通過了 Record<string, unknown> 的驗證

// 如果你用 as Record<string, unknown>，全部變成 unknown

7. satisfies vs as — 完整比較

as Typesatisfies Type
語意「把這當作 Type」「檢查這是 Type，但保留原本型別」
驗證✅ 通過✅ 通過
拓寬？✅ 會拓寬❌ 不拓寬
保留 literal❌ 失去✅ 保留
什麼時候用你比編譯器更清楚你想要型別安全 + 精確型別

8. 面試完整回答

"satisfies（TS 4.9+ 引入）讓我可以檢查一個值是否符合某個型別，但不會拓寬它。我主要用在三種場景：config 物件、事件對應表、設計 token — 任何我想要型別安全但又需要保留最精確推斷型別的地方。

"as const 則是把陣列或物件的型別收窄到 literal，不讓 TypeScript 把它拓寬成 string[] 或一般物件型別。

"兩個功能可以組合使用 — 例如用 as const 保留 roles 陣列的精確型別，再用 satisfies 確保整個 config 物件符合 Record<string, unknown>。這樣既有安全驗證，又有精確的 autocomplete 和 exhaustive type checking。"

9. 練習題

題目 1：以下兩者的型別差在哪？

const a = { x: 1 } as Record<string, number>;
const b = { x: 1 } satisfies Record<string, number>;

a.x 是 number（被拓寬了）。b.x 是 literal 1（保留了）。兩個都通過型別檢查，但 satisfies 不會丟棄原始的精確型別。

題目 2：以下程式碼，Fruit 是什麼型別？如果沒有 as const 呢？

const fruits = ['apple', 'banana'] as const;
type Fruit = typeof fruits[number];

有 as const：'apple' | 'banana'。沒有 as const：string（陣列被拓寬了）。

題目 3：面試官問：「你用 satisfies 還是用 as？什麼時候用哪個？」請用中文回答。

"預設用 satisfies，因為我想要型別安全又不想失去精確型別。只有在極少數需要 override 型別的時候才用 as — 例如你從 JSON.parse 拿到的資料，你知道它一定是某個型別但 TypeScript 不知道。"
